# 0923 作业：用户登录成功后，如何识别用户身份

**一句话结论**：登录成功后，服务端把一枚**不透明随机会话标识**通过 `Set-Cookie` 下发到浏览器；
之后每次请求浏览器自动在请求头带上这枚 Cookie，服务端用它去 `sessions` 表换回 `user_id`，
再查 `users` 得到 `role` 与 `class_id`，最后用这个 `class_id` 去查本班材料。
**权限与班级从不来自客户端，只来自服务端这次查表的结果。**

截图见同目录 `截图/`，原始网络抓包见 `抓包原始记录.json`。

---

## 一、完整识别链路（5 步）

### 第 1 步：登录成功 → 服务端签发会话标识

`POST /api/login` 用 bcrypt 校验口令，通过后：

1. 生成 32 字节随机数，base64url 编码成**不透明标识**（token）；
2. 对 token 做 `HMAC-SHA256(SESSION_SECRET, token)`，把**结果**作为 `sessions.id` 写库；
3. 通过响应头把 **token 本身**（不是 HMAC）放进 Cookie 下发给浏览器。

实测响应头（`截图/03`，数据来自浏览器 Network 抓包）：

```
Set-Cookie: campusclaw_session=_YYayaJ-lzdeW2Q4fFyrZ7l_K_w7ZlSwYDn1gLu7BPU;
            Path=/; Max-Age=230400; HttpOnly; SameSite=Lax
```

三个属性各有作用：
- `HttpOnly`：JavaScript 读不到，XSS 也偷不走（前端代码里**根本没有**读它的语句）；
- `SameSite=Lax`：跨站请求不会自动带上，降低 CSRF 面；
- `Max-Age=230400`（8 小时）：会话有效期，与服务端 `sessions.expires_at` 一致。

### 第 2 步：之后每个请求，浏览器自动带 Cookie

实测（`截图/03`）：

```
GET /api/materials
  Cookie: campusclaw_session=_YYayaJ-lzdeW2Q4fFyrZ7l_K_w7ZlSwYDn1gLu7BPU
```

注意：这一行**不是前端代码写的**。前端只写 `fetch('/api/materials', { credentials: 'same-origin' })`，
Cookie 由浏览器按同源规则自动附加。

### 第 3 步：服务端鉴权中间件用标识换回身份

每次进入受保护接口前先过 `RequireAuth`（`backend/internal/httpx/httpx.go:60`）：

```go
cookie, err := r.Cookie("campusclaw_session")     // ① 取 Cookie 里的 token
session, err := store.Lookup(r.Context(), cookie.Value)  // ② 换回身份
next.ServeHTTP(w, r.WithContext(WithSession(r.Context(), session)))  // ③ 放进请求上下文
```

`Lookup`（`backend/internal/auth/session.go:76`）做三件事：

```go
// ① 把 token 按同样方式做 HMAC，再拿它去查会话行
WHERE s.id = ?                       // ? = HMAC(SESSION_SECRET, token)
// ② 顺带 JOIN 出用户与班级
JOIN users   u ON u.id = s.user_id
JOIN classes c ON c.id = u.class_id
// ③ 返回 user_id / role / class_id / class_name，并检查 expires_at 是否过期
```

所以"识别用户"这一步实际得到的是一组 **user_id + role + class_id**，而不是一个孤零零的用户名。

### 第 4 步：业务查询用会话里的班级取材料

`GET /api/materials`（`backend/internal/materials/store.go:58`）：

```sql
WHERE m.class_id = ?      -- ? 来自会话，不来自请求参数
```

实测：学生 `student_a1`（A 班）请求后返回的每一条材料 `class_id` 都是 1，
并且**请求里带上 `?class_id=2` 也不会改变结果**（参数被忽略）。

### 第 5 步：没有标识或标识失效 → 401

```
GET /api/materials（不带 Cookie）→ 401 {"error":"unauthorized"}
```

`截图/05` 是浏览器直接访问该接口的实测：响应体不含任何材料标题或正文。

## 二、为什么这样能防住常见攻击

| 关注点 | 本实现 | 说明 |
| --- | --- | --- |
| 标识能不能被伪造 | 不能 | 标识是 32 字节密码学随机数，库中只存 HMAC；猜不到也造不出 |
| 库被读走会怎样 | 仍不能直接冒充 | 表里是 `HMAC(SESSION_SECRET, token)`，没有 `SESSION_SECRET` 反推不出 token（见`截图/04`） |
| 脚本/XSS 能不能偷 | 不能 | `HttpOnly`，前端代码从未读取该 Cookie |
| 能不能改前端绕过 | 不能 | 角色与班级来自 `users` 表；前端 `localStorage` 里没有任何角色/班级信息 |
| 登出后旧标识还能用吗 | 不能 | 登出 `DELETE FROM sessions WHERE id = ?`，旧 Cookie 立即 401 |
| 换人登录会不会沿用旧标识 | 不会 | 登录成功**换发新标识**并作废旧会话，防会话固定 |
| 会话过期 | 服务端删行 | `Lookup` 发现 `expires_at` 已过则删行并返回 401 |

**为什么不用 JWT 放 localStorage**：JWT 的载荷里通常带着 `role`/`class_id`，容易被当成授权依据；
放 localStorage 则脚本可读，一旦 XSS 就被窃取；而且无状态 JWT 在过期前很难作废，登出无法立刻生效，
还得再加一份黑名单，等于绕回服务端会话。本迭代是浏览器同源站点，服务端会话 Cookie 更直接。

## 三、证据与截图对照

| 截图 | 内容 | 来源 |
| --- | --- | --- |
| `01-登录页.png` | 未登录时的登录页 | 浏览器 |
| `02-登录成功后获取本班材料.png` | 登录后材料页，右上角显示 `student_a1（学生）` 与 `A 班`，列表只有本班材料 | 浏览器 |
| `03-登录与取材料请求的网络抓包.png` | 登录响应的 `Set-Cookie`；取材料请求头里的 `Cookie` | 浏览器 Network 抓包（CDP） |
| `04-服务端会话表与身份换回.png` | `sessions` 表内容、`HMAC` 与库中 `id` 完全一致的校验、`/api/me` 返回的身份、按班取材料结果 | 本机命令实测输出 |
| `05-没有会话标识时被拒-401.png` | 不带 Cookie 直接请求材料接口 → 401 | 浏览器 |

`04` 里最关键的一段：把下发的 token 用 `openssl dgst -sha256 -hmac $SESSION_SECRET` 算一遍，
结果与数据库 `sessions.id` **逐字符相同**——这证明库中保存的是 token 的 HMAC，而不是 token 本身；
也就是说，**标识的签发权由 `SESSION_SECRET` 决定，缺失该配置服务会直接启动失败**（不会退回内置默认密钥）。

## 五、边界说明

会话与限流状态目前都在单实例内可用（会话在数据库、登录失败限流在进程内存），因此本迭代只声明**单实例部署**；
多副本需要把限流状态外置。JWT / OAuth / SSO、超级管理员等属于本迭代明确不做项。
