# 0930 课堂任务：token 方案实现登录认证

**实现效果**：登录接口签发 **JWT（HS256）访问令牌 + 可撤销刷新令牌**；
受保护接口既接受 Cookie 会话，也接受 `Authorization: Bearer <token>`；
校验通过后仍按 `sub` 回 `users` 表取 `role` 与 `class_id`。截图见本目录 `截图/`（7 张，浏览器实测）。

演示页：`/token-demo.html`（对真实接口发起请求，未做任何改写）。

## 一、接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/api/token` | 账号口令 → `access_token`(JWT) + `refresh_token` + `expires_in` |
| POST | `/api/token/refresh` | 用刷新令牌换新令牌对，**旧刷新令牌一次性作废（轮换）** |
| POST | `/api/token/logout` | 撤销刷新令牌 |

访问令牌载荷：

```json
{ "sub": 2, "jti": "caa70f5d…", "iat": 1790738760, "exp": 1790739660 }
```

## 二、实现要点

1. **令牌只带 `sub` 与时间戳，不带 `role` / `class_id`。**
   载荷是客户端可读的，把权限声明放进去容易被误当成授权依据；本实现每次请求都按 `sub` 查库取身份，
   与 Cookie 方案走同一条路径（`httpx.RequireAuth` 里两个分支最后都落到 `WithSession(...)`）。
2. **签名与过期都验**：HS256，密钥 `JWT_SECRET` 来自环境变量（缺失则启动失败），
   用 `hmac.Equal` 做常量时间比较；过期即 401。
3. **刷新令牌可撤销**：随机 32 字节，服务端只存 `HMAC(JWT_SECRET, token)`（与迭代 1 的会话标识同一套做法），
   轮换后旧令牌再不可用；登出即删除。
4. **撤销语义写清楚**：访问令牌是无状态的，**登出后它仍会在有效期内可用**（本实现有效期 15 分钟）——
   要立即失效必须引入黑名单，等于回到服务端存储，这与 Cookie 方案的取舍正好相反。
5. 与 Cookie 方案**并存，互不影响**：迭代 1 的登录、登出、限流、班级隔离全部照常。

## 四、与 Cookie 会话方案的对照（本课的重点）

| 维度 | Cookie 会话（迭代 1） | token 方案（本次） |
| --- | --- | --- |
| 凭据存放 | 不透明随机串，服务端有会话行 | JWT 自包含，服务端不存访问令牌 |
| 登出能否立即失效 | 能（删会话行） | **访问令牌不能**，只能等过期；刷新令牌可撤销 |
| 浏览器自动携带 | 是 | 否，需要代码显式加 `Authorization` 头 |
| 脚本可读 | 否（HttpOnly） | 取决于存放位置，放 localStorage 则 XSS 可读 |
| 授权依据 | 每次查库 | 同样每次查库（**不采信令牌载荷**） |
| 适合场景 | 同源浏览器站点 | 开放 API、移动端、多方调用 |
