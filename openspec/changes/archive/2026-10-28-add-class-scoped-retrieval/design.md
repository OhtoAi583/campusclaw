# Design: 限定班级范围的知识库检索与内容溯源（迭代 2）

## Context

迭代 1 之后，系统中已有：按班级隔离的材料与正文（`materials` / `knowledge_entries`，`class_id` 非空且带索引）、
服务端会话身份（`user_id` / `role` / `class_id`）、以及"下载必须走鉴权接口"的既定约定。
本迭代在这之上加检索，因此有两条不可退让的前提：

1. **检索范围必须与迭代 1 的隔离同一条边界**：租户标识只来自会话，任何请求参数都不能扩大范围；
2. **每条结果必须可溯源**：能指回具体材料与具体片段，否则后续的智能能力无法引用证据。

数据规模按课程场景设计：单实例、单机 MySQL、材料数百条、正文总量数十万字。

## Decisions

### Decision 1: 检索边界沿用会话班级（D1）

检索的候选集合是 `WHERE class_id = <会话班级>`，班级只来自 `sessions → users`，请求体里的 `class_id` 一律忽略。
召回在 SQL 层就完成班级过滤，应用层再做二次断言，两道都要有。

备选：先全库召回再在应用层过滤班级。否决理由：一旦过滤分支写错就会把其他班级的正文回给调用方，
而且日志、耗时、结果数都会泄漏跨班数据的存在性；正确做法是让跨班数据从一开始就不进入候选集。

### Decision 2: 块（chunk）是检索与溯源的最小单位（D2）

把 `knowledge_entries.content` 切成带**字符区间**的块：`kb_chunks(material_id, class_id, chunk_index, start_offset, end_offset, content, embedding)`。
分块策略为"按 Markdown 标题优先切分，超长段落再按固定长度 + 重叠切分"，块大小与重叠走配置。

溯源直接复用块的 `start_offset / end_offset`：片段原文必须与材料正文在该区间上的子串逐字符一致，
这样前端才能回到详情页定位并高亮。

备选：以整篇材料为单位做向量。否决理由：整篇材料对应一个向量时，命中只能定位到"某篇"，
无法给出"哪一段"，也就没有可核对的内容溯源，且长文档向量会被稀释。

### Decision 3: 本迭代使用本地确定性嵌入，不引入外部 embedding 服务（D3）

嵌入在进程内计算：对片段做字符 n-gram 分词后，用**哈希技巧（hashing trick）映射到固定维度的稀疏向量**，
再做 L2 归一化。维度由 `EMBEDDING_DIM` 配置（默认 512）。
嵌入接口做成可替换的实现（`Embedder` 接口），后续迭代可以换成真实语义模型而不改上层。

- 优点：可离线、可复现（同样输入必然得到同样向量）、无密钥、无网络依赖、CPU 开销小；
  检索质量足以支撑"同主题命中"，并且**排序可判定**，评测集能稳定复现。
- 局限：它是词形层面的相似，不具备真正的语义泛化；这一点写进 README 的已知限制。

备选一：调用云端 embedding API。否决理由：需要密钥与网络、结果随模型版本漂移、无法离线复现，与"第三方按 README 从零复现"冲突。
备选二：本地跑小尺寸语义模型（ONNX / sentence-transformers）。否决理由：镜像体积与依赖显著变大，
且推理时间会让"单实例、同步索引"的设计变得脆弱；留到后续迭代再评估。

### Decision 4: 向量存 MySQL，相似度在应用层计算（D4）

向量以定长 `BLOB`（`float32` 小端，长度 = `EMBEDDING_DIM × 4`）存在 `kb_chunks.embedding`；
召回时按班级取出候选向量，在 Go 里算**余弦相似度**排序取 `top_k`。
由于向量已 L2 归一化，余弦相似度退化为点积，计算足够快。

备选一：引入向量数据库（Milvus / Qdrant / Weaviate）。否决理由：单实例课程场景要多维护一个组件与一份数据卷，
且"按班级过滤"在外部库里要额外保证与 MySQL 一致，反而增加隔离出错面；数据量级也用不上 ANN 索引。
备选二：用 MySQL 9 的 `VECTOR` 类型与向量距离函数。否决理由：交付形态固定 `mysql:8.0`，该类型不可用；
换成 9.x 会同时改变迭代 1 的已验证环境。
备选三：把向量交给缓存/内存索引。否决理由：进程重启即失效，与"重建幂等、可持久"的要求冲突。

### Decision 5: 索引与材料入库同一事务（D5）

上传材料时，`materials`、`knowledge_entries`、`kb_chunks` 三张表在**同一事务**里写入；
分块与嵌入在落盘前完成计算（纯 CPU，不涉及外部调用），任一步失败整体回滚并删除已写入的文件，
沿用迭代 1 的"无文件、无记录"语义。

备选：异步/队列建索引。否决理由：会引入"材料已存在但检索不到"的中间态，无法判定，也需要额外的重试与补偿机制。

### Decision 6: 索引可幂等重建（D6）

提供重建入口（命令或内部函数）：按 `material_id` 先删该材料的旧块、再按当前正文重新生成。
重复执行不产生重复块，且对同样的正文产生同样的分块数量与区间。

备选：不做重建，只依赖上传时写入。否决理由：种子数据、迭代 1 已入库的历史材料、以及分块参数调整后都需要补建。

### Decision 7: 溯源字段与"不泄露"边界（D7）

每条结果返回：`material_id`、`material_title`、`original_name`、`chunk_index`、`start_offset`、`end_offset`、
`content`（片段原文）、`score`。

**不返回**：`stored_name`（服务端存储名）、任何磁盘路径、`class_id` 之外的租户信息。
片段正文本身属于"用户有权看的内容"（同班），因此可以返回；文件下载仍然必须走迭代 1 的鉴权接口。

备选：只返回材料 id 与分数，让前端再拉一次详情取片段。否决理由：前端还要自己截取片段并保证与检索一致，
既多一次请求又容易出现"检索显示的片段与详情不一致"。

### Decision 8: 空结果与越权的语义（D8）

- 查询合法但没有命中 → **200 + 空数组**（不是 404：这是"没有匹配"，不是"资源不存在"）；
- 未登录 → **401**（沿用迭代 1 的默认拒绝）；
- 查询参数非法（空查询、超过长度上限、`top_k` 超过上限）→ **400**；
- 检索依赖不可用或超时 → **503**。

跨班内容既不进入候选集，也不体现在"结果数"或错误信息里；因此**不存在"跨班 404"这一分支**——
这正是与迭代 1 对象级授权的区别：那边是"按 ID 取一个对象"，这边是"在一个集合里召回"。

### Decision 9: 检索日志只记录必要信息（D9）

每次检索记录：`user_id`、`class_id`、查询长度、候选数、返回结果数、耗时。
**不记录**查询原文与片段正文：查询原文可能包含未公开的命题草稿，正文属于学生数据。

备选：完整记录查询语句以便排障。否决理由：日志本身会变成新的数据泄漏面。

## Interface Overview

| 方法 | 路径 | 鉴权 | 成功 | 失败 |
| --- | --- | --- | --- | --- |
| POST | `/api/search` | 会话 | 200 + 结果数组 | 401 / 400 / 503 |

请求体：

```json
{ "query": "阅读课 导入环节", "top_k": 5 }
```

响应体：

```json
{
  "query": "阅读课 导入环节",
  "class_id": 1,
  "count": 1,
  "items": [
    {
      "material_id": 1,
      "material_title": "A班·教研材料示例：语文阅读课教学设计",
      "original_name": "A班-语文阅读课教学设计.md",
      "chunk_index": 0,
      "start_offset": 0,
      "end_offset": 120,
      "content": "……被命中的片段原文……",
      "score": 0.83
    }
  ]
}
```

## Data Model

- `kb_chunks`
  - `id`、`material_id`（外键，级联删除）、`class_id`（**非空 + 索引**，与材料一致）
  - `chunk_index`（该材料内序号，`(material_id, chunk_index)` 唯一，支撑幂等重建）
  - `start_offset`、`end_offset`（相对 `knowledge_entries.content` 的字符区间）
  - `content`（片段原文）、`embedding`（定长 BLOB）、`embedding_dim`（写入时的维度，便于检测配置变更）
  - `created_at`

## Configuration & Startup

新增配置项，同样只从环境变量读取，`.env.example` 列出：

| 变量 | 含义 | 默认 |
| --- | --- | --- |
| `EMBEDDING_DIM` | 向量维度，必须为正偶数且为嵌入实现支持的值 | 512 |
| `CHUNK_SIZE` | 单个块的目标字符数 | 600 |
| `CHUNK_OVERLAP` | 相邻块的重叠字符数，必须小于 `CHUNK_SIZE` | 80 |
| `SEARCH_TOP_K_MAX` | 单次检索允许的最大返回条数 | 20 |
| `SEARCH_QUERY_MAX_CHARS` | 查询长度上限 | 200 |
| `SEARCH_TIMEOUT_MS` | 单次检索超时 | 1500 |

`EMBEDDING_DIM` 与库中 `kb_chunks.embedding_dim` 不一致时启动失败并提示先重建索引，
避免"配置换了维度但旧向量还在"导致检索结果不可解释。

## Quality Gate（评测集）

`eval/retrieval-cases.json` 固定若干条查询与期望来源（材料标题 + 关键词），
验收时同时判定两件事：**命中率**（期望来源出现在前 K 条）与**隔离**（B 班关键词在 A 班检索结果必须为空）。
