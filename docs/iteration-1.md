# 迭代 1 说明：认证授权与知识库入库

本迭代交付 CampusClaw 的底座：登录、角色权限、班级数据边界、材料上传与知识库正文入库。
决策与 `openspec/changes/add-auth-upload-isolation/design.md` 保持一致，本文用可独立阅读的方式再写一遍。

## 一、四项设计决策

### 决策 1：班级从哪里来

**上下文**：同一个数据库实例里放多个班级的数据，必须有一个"租户标识"决定每条数据归谁。

**决策**：租户标识只来自服务端会话——请求先按会话查出 `user_id`、`role`、`class_id`，
列表查询写成 `WHERE class_id = <会话班级>`，上传落库也取会话班级。
请求里出现的 `class_id`、`role` 等字段一律忽略。

**备选与否决理由**：备选是让前端在请求参数里带上 `class_id`，后端按参数查询。
否决理由：这等于把租户边界交给客户端，攻击者改一个参数就能读别的班；而且前端"少渲染一个入口"
只是降低了误操作概率，不构成访问控制。

### 决策 2：跨班返回 403 还是 404

**上下文**：用户已登录、身份合法，只是访问了不属于自己班级的对象。这属于对象级授权失败（BOLA / IDOR）。

**决策**：**返回 404**，并且与"记录不存在"的响应逐字节一致；真实原因写入服务端日志。
实现上先按 ID 取出行，再核对 `class_id`，两条分支调用同一个 `notFound()`。

**备选与否决理由**：备选是返回 403，排障时能直接看出"资源存在但你没权限"。
否决作为默认的理由：403 会承认资源存在，攻击者可以据此遍历 ID 枚举资源；排障需求改由服务端审计日志满足。

### 决策 3：上传失败如何避免脏数据

**上下文**：一次上传要动两个地方——磁盘上的原文件，和数据库里的 `materials` + `knowledge_entries` 两行。

**决策**：先做完所有校验（白名单扩展名、大小上限、非空且合法 UTF-8），再落盘；
随后在**同一个事务**里写两张表。事务失败就回滚并删除刚落盘的文件，
最终状态只有两种：要么"文件 + 两行记录"齐全，要么"什么都没有"。

**备选与否决理由**：备选是"先写文件，再异步/稍后入库"。否决理由：中间态会让第 4 课的检索
读到没有正文的记录，或者让下载指向不存在的文件——出现无法判定的半成品。清理逻辑必须写进规约才可验收。

### 决策 4：`/health` 是否检查数据库

**上下文**：容器编排需要一个探针判断服务是否可用，但"进程活着"和"依赖可用"是两件事。

**决策**：`/health` 公开、**不查库**，只回答进程是否存活。
数据库故障表现为受保护接口不可用（503），而不是把已登录用户判为会话失效（401），也不触发容器反复重启。

**备选与否决理由**：备选是在 `/health` 里直接 ping 数据库。否决理由：把存活与就绪混成一个语义，
数据库抖动会导致容器被判死并重启，反而放大故障；两者要分开表达。

## 二、三条被否决的交付做法

1. **"一次提示词生成整仓"**：速度快，但规约与实现会一起漂移，出问题无法定位是规约不清还是实现偏离。
   本迭代按 `tasks.md` 一条一条做，每条都有可执行的 verify。
2. **"只交规约、不做可运行交付"**：设计再完整，第三方按 README 启动不了就不算发布。
   本迭代的标准启动方式是 Docker Compose，且必须能被别人从零复现。
3. **"多人共用仓库提交"**：协作方便，但责任不清——出了问题无法定位到人。
   本迭代要求独立提交；互相验证用"同伴交叉验证"（读到对方仓库，用预置账号试一条跨班 URL），
   而不是共用一个仓库。

## 四、已知限制

- 登录失败限流在进程内存中，因此**只支持单实例**部署；多副本需要把限流状态外置。
- 会话表在数据库中，登出与过期清理都依赖数据库可用；数据库故障时表现为 503。
- 本迭代的知识库只保存正文，没有检索与问答能力（见 Non-goals）。
- 本地验证环境用的是 Homebrew 安装的 MySQL（26.7）与 nginx；Compose 交付固定 `mysql:8.0`，
  两者在本文涉及的 SQL 与 HTTP 行为上一致。
